## Problem Statement

用户每天在微信公众号和小红书上看到大量有价值的内容（文字 + 图片/截图），但：
- 内容碎片化、片面化，单独看完一篇并不会真正吸收
- 缺少把碎片"展开"成完整知识的工具
- 在通勤/做家务的时间想用耳朵学，但内容不是音频形态

目标：一个微信内即开即用的小工具，输入碎片 → 输出可听可读的完整学习材料。

## What Makes This Cool

- **入口零摩擦**：微信里直接打开，拍图/粘贴/上传，不切换 App
- **从碎片到完整**：AI 带着联网信息把原文背景、相关主题、批判视角全展开
- **双人对话播客**（NotebookLM 体验）：两个 AI 主持人聊这个主题
- **锁屏控件原生支持**：BackgroundAudioManager 自动接管系统播放控件
- **闭环短**：输入 → 等 3-5 分钟 → 收订阅消息 → 听

## Constraints（基于官方文档核实）

### 微信小程序侧
- 个人主体可注册、当天拿 AppID、当天用上「体验版」
- 体验版无需小程序备案、无需类目合规
- 个人主体禁止：微信支付、朋友圈分享、微信认证
- AI 类目（深度合成）个人主体不开放——所以**永远只用体验版，不上架**
- ⚠️ 类目选择：申请时建议选"工具 / 教育"，避开"AI 对话/智能助手"敏感类目

### CloudBase 侧（关键约束 — 这是重点）
- **同步云函数超时上限 60s，但小程序 SDK 端硬上限 15s**——长任务必须异步化
- **异步云函数最长 900s（15 分钟）**——但需付费开通"自定义超时/内存"
- 个人版 ¥19.9/月：3GB 存储 + 1500 万 CU 计算 + 1000 并发，无固定出口 IP
- 标准版 ¥199/月：才有固定出口 IP + `wx.cloud.extend.AI` 自定义模型支持
- 云函数出网无白名单，但直连境外 API（Anthropic / ElevenLabs）**不稳定**
- 云函数互调"不 await"实现 fire-and-forget 是社区惯用法，**需实测验证可靠性**

## Premises（已根据 CloudBase 文档全面修正）

1. ✅ 个人工具，永远只发体验版（你 + ≤89 位体验成员），不上架
2. ✅ 后端用 **CloudBase 个人版（¥19.9/月）**，绕过域名/SSL/备案/白名单
3. ✅ 长任务必须拆成 **3 个云函数**：createTask（同步快返）+ processTask（异步长跑）+ cronCleanup（兜底）
4. ✅ **三类模型（识图 / 文本 / 语音）均不预先绑定**——设计上做 provider 抽象，先对比测试再决定
5. ✅ 优先评估**国产已备案模型**（云函数直连稳，合规风险低），把境外模型当兜底/对照
6. ✅ TTS 是最大成本头（占总成本 70%+），值得单独多花时间做对比
7. ✅ 音频文件存云存储 → 拿 fileID → 客户端 `getTempFileURL` 换 https → BackgroundAudioManager
8. ✅ 状态同步走 `db.watch()` 实时监听，不轮询
9. ✅ 文末固定"由 AI 生成，仅供学习参考"标识
10. ✅ **用户身份 onboarding**：首次进入小程序时设置身份（学生 / PM / 开发 / 等），所有播客自动按该身份视角生成；设置页可改身份
11. ✅ **播客时长**：开发期 5-7 min（省 TTS 成本 + 快速迭代），生产期切到 20 min（适合通勤、家务等真实使用场景）
12. ✅ **重生成功能**：详情页有"重新生成"按钮 + 自由文字反馈输入框，用户能直接说"哪里不对、想怎么改"
13. ✅ **不懂的词解释**：MVP 不做专门勾选环节，依赖 AI 自动判断（基于身份）；如果实际用下来漏词多，v2 再加

#### 开源 TTS 的 4 种使用路径（按上手难度排序）

| 路径 | 操作 | 上手 | 月成本（1 篇/天） | 适合 |
|---|---|---|---|---|
| **A. 托管端点**（Replicate / fal.ai / HuggingFace） | 调 HTTP API，跟商业 TTS 一样 | 低 | ¥10-30 | **推荐** |
| **B. Tencent CloudBase Cloud Run 容器** | 自己打 Docker 镜像，部到云托管 | 中-高 | ¥30-80 | 想压成本 |
| **C. 腾讯云 GPU 实例自部署** | 装 CUDA、跑模型、暴露 API | 高 | ¥200+（GPU 包月） | 想全自主 |

### 评估方法（一套测试集，逐一打分）

**统一测试集**（5 篇真实素材）：
1. 一张小红书截图（长文，纯文字）— 测中文 OCR + 视觉模型理解
2. 一张小红书截图（图文混排 + emoji + 标签）— 测复杂版面识别
3. 一段公众号纯文字（3000 字理论文章）— 测 LLM 概念提取 + 拓展
4. 一段公众号叙事内容（个人故事 + 观点）— 测 LLM 改写成对话的自然度
5. 一段已生成的对话脚本（5 分钟，30 个 turn）— 测 TTS 拼接连贯感

**评分维度**（每项 1-5 分）：

识图模型：
- 中文识别准确率（数字、emoji、专业术语）
- 版面理解（标题、正文、引用分块）
- 主题概括能力
- 单次响应时间（云函数视角）
- 单次成本

文本模型：
- 信息完整性（没漏关键点）
- 结构合理度（章节划分）
- 联网补充质量（不水文）
- 对话改写自然度（不像念稿）
- 中文写作风格（不机翻味）
- 单篇成本

TTS 模型：
- 中文发音准确率
- 语调自然度（不像新闻联播）
- 双人区分度（音色不混淆）
- 对话节奏（停顿、转场）
- 单篇成本
- 单次合成时间

**决策规则**：识图选总分 Top 2、文本选总分 Top 2、TTS 选总分 Top 1（因为 TTS 影响最终听感最大）。最终运行时**支持两两组合切换**，长期可能多模型混用（比如平时 DeepSeek-V3，深度内容用 R1）。

## Development Workflow（vibe coding 路径）

**核心结论**：Claude Code 完全胜任这个项目。CloudBase 有官方 MCP，Claude Code 通过 MCP 能完成 95% 的后端工作；剩下 5%（小程序代码包上传）走微信开发者工具或 `miniprogram-ci` CLI。

### 三种工作流对比

| 维度 | A: 纯 Claude Code + MCP | B: 纯 CodeBuddy | C: Claude Code + 微信开发者工具（推荐⭐） |
|---|---|---|---|
| 上手难度 | 中（写 `.mcp.json` 30 分钟） | 最低（一键登录） | 中 |
| 全流程覆盖 | 95%（差小程序上传） | 95%（同一窗口上传） | **100%** |
| 代码生成质量 | Claude 4.6/4.7 Sonnet **业内最强** | 国内版 DeepSeek（弱一档），国际版要付费 | 用 Claude Code 即业内最强 |
| Agent 自主性 | 强（你已经用顺） | 较弱（多步任务容易卡） | 强 |
| 卡住时的可调试性 | 高 | 中（Agent 弱 → 不会代码的人没法救场） | 高 |
| 工具锁定 | 无 | 完全锁腾讯生态 | 无 |
| 月成本 | Claude Code 订阅 + 国内代理 | 免费（DeepSeek 不限量） | Claude Code 订阅 + 国内代理 |
| 是否符合"你已经顺手" | ✅ | ❌（换 IDE） | ✅ |

**推荐方案 C** —— Claude Code 主驾驶，CloudBase MCP 副驾驶，微信开发者工具仅用于"扫码预览 + 上传体验版"。CodeBuddy 留备用。

### 为什么不选纯 CodeBuddy

虽然 CodeBuddy 配置零摩擦，但有两个对你致命的劣势：
1. **Agent 实测稍弱于 Claude Code**——多步骤复杂任务容易卡。你不写代码，Agent 一旦卡住没法手动救场。
2. **换 IDE 的认知负担**——你说 Claude Code 更顺手，迁移成本不为零。
配置便利换来的"快 30 分钟"，远不如代码质量和 Agent 自主性的差距大。

### Claude Code + CloudBase MCP 完整配置步骤

|---|---|---|

| 腾讯云账号 | 注册即可 | cloud.tencent.com |

```json
{
  "mcpServers": {
    "cloudbase": {
      "command": "npx",
      "args": ["@cloudbase/cloudbase-mcp@latest"],
      "env": {
        "INTEGRATION_IDE": "ClaudeCode",
        "TENCENTCLOUD_SECRETID": "AKIDxxxxxxxx",
        "TENCENTCLOUD_SECRETKEY": "xxxxxxxx",
        "CLOUDBASE_ENV_ID": "xueban-prod-xxx"
      }
    }
  }
}
```

⚠️ **重要**：把 `.mcp.json` 加进 `.gitignore`，避免密钥泄漏。

**Step 3 — 注入 CloudBase 最佳实践规则集**

```bash
npx skills add tencentcloudbase/cloudbase-skills -y
```

这一步会在项目根目录生成 / 追加 `CLAUDE.md`，把 CloudBase 的最佳实践告诉 Claude，让它写代码时少踩坑。

**Step 4 — 在 Claude Code 里验证 MCP 连通**

```
列出我当前的 CloudBase 环境信息
```

如果返回环境列表 = 配置成功。

如果不识别，手动注册：
```bash
claude mcp add cloudbase -- npx @cloudbase/cloudbase-mcp@latest
```

**Step 5 — 开始 vibe coding**

直接用自然语言对 Claude Code 描述任务，例如：

```
- 帮我用 CloudBase 的微信小程序模板初始化项目，AppID 是 wxXXXXXX
- 在 cloudfunctions/ 下创建 createTask、processTask、cronCleanup 三个函数，
  按 DESIGN.md 第 N 节的架构
- 给 processTask 配置 timeout=900s, memory=1GB
- 部署到云端
- 帮我创建 tasks 集合，设置安全规则：只允许云函数写，用户只能读自己的
```

Claude Code 通过 MCP 直接完成部署。

**Step 6 — 小程序代码包上传（每次发版）**

### 典型踩坑预警

### 关键技术决策表（基于核实结果修正）

| 决策点 | 原假设 | 修正（基于官方文档） |
|---|---|---|
| 同步等待 | callFunction 等到结果 | **不行**：SDK 端 15s 上限，必须异步化 |
| 长任务 | 一个云函数搞定 | **拆成 createTask + processTask** |
| 状态查询 | 客户端轮询 | **`db.watch()` 实时监听** |
| 函数互调 | 没考虑 | **fire-and-forget**（不 await）+ cron 兜底 |
| LLM 选型 | Claude API | **改为 Qwen-VL-Max + DeepSeek**（国内直连稳 + 中文更准 + 便宜 5-10 倍 + 已备案） |
| LLM 调用方式 | 直连 Anthropic | **直连 DashScope / DeepSeek 国内 API**，无需中转 |
| TTS 选型 | ElevenLabs 优先 | **改为 MiniMax 海螺 / 阿里云**（国内稳） |
| AI 工具箱 | `wx.cloud.extend.AI` 直接接外部 LLM | **个人版不支持自定义模型**，必须云函数自己 fetch |
| 出口 IP | 没考虑 | **个人版无固定 IP**——纯 API Key 鉴权（DeepSeek / DashScope / MiniMax 都支持） |
| 订阅消息 | 后端 push | **一次性订阅**，每次按钮点击触发授权 |
| 客户端拿音频 | 直接 https URL | **fileID + getTempFileURL（2 小时有效）** |

async function submitImage() {
  const { tempFiles } = await wx.chooseMedia({ count: 1, mediaType: ['image'] })
  const { tempFilePath } = await wx.compressImage({
    src: tempFiles[0].tempFilePath, quality: 75
  })
  
  // 直传云存储（不经云函数中转，省流量）

    filePath: tempFilePath

  await wx.requestSubscribeMessage({ tmplIds: [TASK_DONE_TMPL_ID] })

  // 同步入队（<5s 返回）
  const { result } = await wx.cloud.callFunction({
    name: 'createTask',
    data: { inputType: 'image', fileID }
  })
  const { taskId } = result

  // 实时监听状态
  const db = wx.cloud.database()
  const watcher = db.collection('tasks').doc(taskId).watch({
    onChange: snapshot => {
      const task = snapshot.docs[0]
      if (task.status === 'done') {
        watcher.close()
        navigateToPlayer(task.audioFileID, task.title)
      } else if (task.status === 'failed') {
        watcher.close()
        wx.showToast({ title: '生成失败，请重试', icon: 'error' })
      }
    }
  })
}

### 云函数核心代码

```javascript
// cloudfunctions/createTask/index.js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

exports.main = async (event) => {
  const { OPENID } = cloud.getWXContext()
  const taskId = generateId()
  
  await db.collection('tasks').add({
    data: {
      _openid: OPENID,
      taskId,
      inputType: event.inputType,
      inputFileID: event.fileID,
      inputText: event.text,
      status: 'pending',
      createdAt: db.serverDate()
    }
  })

  // fire-and-forget: 不 await
  cloud.callFunction({
    name: 'processTask',
    data: { taskId }
    // 注意：wx-server-sdk 的 callFunction 默认是同步的，
    // 实现 fire-and-forget 的常见做法是直接不 await，让 promise 自然结束。
    // 替代方案：直接结束当前函数前调用，让 Node 事件循环自己继续。
  }).catch(() => {})  // 忽略错误，processTask 会自己处理

  return { taskId }
}
```

```javascript
// cloudfunctions/processTask/index.js
// 配置：timeout=900s, memory=1GB
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

// Provider 抽象层：切换模型只改环境变量，不改业务代码
const visionProvider = require('./providers/vision')[process.env.VISION_PROVIDER || 'qwen-vl-max']
const textProvider   = require('./providers/text')[process.env.TEXT_PROVIDER   || 'deepseek-v3']
const ttsProvider    = require('./providers/tts')[process.env.TTS_PROVIDER     || 'minimax']

exports.main = async ({ taskId }) => {
  const taskDoc = db.collection('tasks').doc(taskId)
  try {
    const task = (await taskDoc.get()).data

    // 1. 看图（如果是图片输入）
    let seedContent = task.inputText
    if (task.inputType === 'image') {
      const file = await cloud.downloadFile({ fileID: task.inputFileID })
      const imageBase64 = file.fileContent.toString('base64')
      seedContent = await visionProvider.describe(imageBase64)
    }

    // 2. 写学习资料 + 对话稿
    const { article, dialogue } = await textProvider.generate(seedContent)

    // 3. 双人 TTS 合成
    const fullMp3 = await ttsProvider.synthesizeDialogue(dialogue)

    // 4. 上传云存储
    const upload = await cloud.uploadFile({
      cloudPath: `audio/${taskId}.mp3`,
      fileContent: fullMp3
    })

    // 5. 更新状态
    await taskDoc.update({
      data: {
        status: 'done',
        title: article.title,
        article,
        dialogue,
        audioFileID: upload.fileID,
        finishedAt: db.serverDate()
      }
    })

    // 6. 发订阅消息
    await cloud.openapi.subscribeMessage.send({
      touser: task._openid,
      templateId: process.env.TMPL_ID,
      page: `pages/player/index?taskId=${taskId}`,
      data: {
        thing1: { value: article.title.slice(0, 20) },
        time2: { value: new Date().toLocaleString('zh-CN') }
      }
    })

  } catch (err) {
    console.error(err)
    await taskDoc.update({ data: { status: 'failed', error: String(err) } })
  }
}

### Skill 化的内容生成管线（关键：可调优、可热替换）

不要把"三类补充 + 综合 + 对话稿"塞进一个超大 prompt。拆成 **5 个独立的 skill 文件**，每个 skill 是一份 markdown，前面是 YAML 元数据，后面是指导内容 + 示例。

**为什么这么拆**：
- 每个 skill 可以**单独优化**而不影响其他步骤（改"批判视角"的 prompt 不会动到"主笔"）
- 可以为**不同 skill 配不同模型**（批判视角用 DeepSeek-R1 推理强，主笔用 DeepSeek-V3 写得流畅）
- skill 文件是**纯文本**，Claude Code 能直接读写，你想调整提示词只需让 Claude Code 改对应文件
- Claude API 原生支持 [Agent Skills](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview)（2025-10 发布）；国产 LLM 没原生 skill 机制，但可以**把 skill 文件内容当 system prompt 加载**，效果等价

**目录结构**：

```
cloudfunctions/processTask/
  skills/
    01-extract-concepts.skill.md     # 提取原文关键概念
    02-add-background.skill.md       # 补背景知识
    03-expand-related.skill.md       # 拓展相关主题
    04-critical-perspective.skill.md # 挖批判视角
    05-synthesize-article.skill.md   # 综合写学习资料
    06-write-dialogue.skill.md       # 改写成双人对话
  providers/
    vision/...
    text/...
    tts/...
  index.js
```

## 输出格式（严格 JSON）

```json

- 不要为反对而反对——只列**真有说服力**的质疑
- 标出**反对论点的强度**（弱/中/强）
- 如果原文已经自我反驳过某个角度，不要重复

**skill 加载器（云函数里）**：

// cloudfunctions/processTask/skills/loader.js
const fs = require('fs')
const path = require('path')
const matter = require('gray-matter')

function loadSkill(name) {
  const filePath = path.join(__dirname, `${name}.skill.md`)
  const raw = fs.readFileSync(filePath, 'utf8')
  const parsed = matter(raw)
  return {
    meta: parsed.data,       // { name, description, preferred_model, max_tokens, ... }
    instruction: parsed.content  // skill 主体（markdown）
  }
}

module.exports = { loadSkill }
```

**主流程改写（用 skill 串管线）**：

```javascript
// cloudfunctions/processTask/index.js（核心改动）
const { loadSkill } = require('./skills/loader')
const textProviders = require('./providers/text')

async function runSkill(skillName, input, providerOverride) {
  const skill = loadSkill(skillName)
  const provider = textProviders[providerOverride || skill.meta.preferred_model || process.env.TEXT_PROVIDER]
  return provider.runWithSkill({
    systemPrompt: skill.instruction,
    userInput: input,
    options: {
      max_tokens: skill.meta.max_tokens,
      temperature: skill.meta.temperature,
      response_format: { type: 'json_object' }
    }
  })
}

// 主流程
async function enrichContent(seedContent) {
  // 第一步：抽概念（基础）
  const concepts = await runSkill('01-extract-concepts', seedContent)

  // 第二、三、四步：并行三种补充
  const [background, related, critical] = await Promise.all([
    runSkill('02-add-background', { seedContent, concepts }),
    runSkill('03-expand-related', { seedContent, concepts }),
    runSkill('04-critical-perspective', { seedContent, concepts }, 'deepseek-r1')  // 这步指定用推理模型
  ])

  // 第五步：综合主笔
  const article = await runSkill('05-synthesize-article', {
    seedContent, background, related, critical
  })

  // 第六步：改写对话
  const dialogue = await runSkill('06-write-dialogue', { article })

  return { article, dialogue }
}
```

### Skill 系统的好处（对你具体意味着什么）

1. **你可以让 Claude Code 直接读写 skill 文件**——发现某次"批判视角"写得太软，直接告诉 Claude Code "去把 `04-critical-perspective.skill.md` 改严厉一点"，根本不动业务代码
2. **每个 skill 可以单独 A/B 测试**——同样的输入跑 DeepSeek-V3 vs DeepSeek-R1 vs Qwen-Max，看哪个写得最好
3. **skill 文件可以版本管理**——git 里能看到每次提示词调优的历史
4. **未来扩展容易**——想加"反向 fact-check"步骤？只需新建 `07-factcheck.skill.md`，主流程加一行
5. **跨模型迁移零成本**——所有 skill 都是 markdown，DeepSeek 用得不爽切 Qwen，只改 `preferred_model` 字段

const fetch = require('node-fetch')
const PROMPT = (seed) => `
原文：${seed}

请基于上述内容，完成三件事：
1. 补充背景知识、相关主题拓展、批判视角（自己判断三者比例）

// providers/tts/minimax.js
const fetch = require('node-fetch')
const VOICES = { A: 'male-qn-qingse', B: 'female-shaonv' }

module.exports = {
  name: 'MiniMax 海螺',
  // 统一接口：传 dialogue 数组，返回拼好的完整 mp3 buffer
  async synthesizeDialogue(dialogue) {
    const buffers = await Promise.all(dialogue.map(({ speaker, text }) =>
      this._one(text, VOICES[speaker])
    ))
    return Buffer.concat(buffers)
  },
  async _one(text, voiceId) {
    const resp = await fetch('https://api.minimax.chat/v1/text_to_speech', {
      method: 'POST',
      headers: {
        'Authorization': `Bearer ${process.env.MINIMAX_API_KEY}`,
        'Content-Type': 'application/json'
      },
      body: JSON.stringify({
        model: 'speech-01',
        text,
        voice_id: voiceId,
        audio_setting: { format: 'mp3', sample_rate: 32000 }
      })
    })
    return Buffer.from(await resp.arrayBuffer())
  }
}

// providers/tts/chattts-replicate.js — 开源模型的 provider 长这样
// 看：跟 minimax.js 在结构上完全一致，只是端点和参数不同
const Replicate = require('replicate')

module.exports = {
  name: 'ChatTTS (开源, 托管在 Replicate)',
  async synthesizeDialogue(dialogue) {
    const replicate = new Replicate({ auth: process.env.REPLICATE_API_TOKEN })
    
    // ChatTTS 支持双人对话，把整段 dialogue 转成它的格式
    const conversation = dialogue.map(({ speaker, text }) => ({
      speaker: speaker === 'A' ? 'speaker_0' : 'speaker_1',
      text: addProsody(text)  // 注入语气词 token [laugh] [uv_break] 等
    }))
    
    // Replicate API 调用（pollingless 版本）
    const output = await replicate.run(
      '2noise/chattts:latest',
      { input: { conversation, sample_rate: 24000 } }
    )
    
    // 拿到的是音频文件 URL，下载成 buffer
    const audioResp = await fetch(output.audio_url)
    return Buffer.from(await audioResp.arrayBuffer())
  }
}

function addProsody(text) {
  // 简单插入停顿和语气，让 ChatTTS 表现更自然
  return text
    .replace(/[，。]/g, '$& [uv_break] ')
    .replace(/(哈哈|呵呵)/g, '[laugh] $1')
}

## Development Sequence（vibe coding 的工作流哲学）

Vibe coding 的开发顺序和传统流程**不一样**。不要走瀑布（PRD → UI → 后端 → 联调），也不要"先设计后开发"。遵循 **reverse-risk**：先解决最不确定的事。

### 为什么这个项目要"后端先于 UI"

你需要的 4 个屏幕（输入 / 列表 / 详情 / 播放器）都是已知模式。后端有 10 倍的未知：
- Fire-and-forget 云函数可靠性
- 哪个 TTS 听起来像真播客
- AI 写的学习资料是否值得听
- 各模型组合的真实成本
- 6 个 skill 的 prompt 怎么调

如果第 1 周结束时"听了 5 个候选 TTS 都不像真人"——**项目就死了**。最好在写 UI 之前发现这件事。

### 四阶段反风险节奏

```
Phase 1 (Week 1): 后端骨架 + 模型对比
   ↓ 问题："听起来像真播客吗？"
Phase 2 (Week 2): 又丑又能跑的端到端
   ↓ 问题："手机上真的能用吗？"
Phase 3 (Week 3): 真实使用 7 天
   ↓ 问题："实际用起来什么最烦？"
Phase 4 (Week 4+): 基于真实摩擦的体验打磨
```

### Phase 1：后端骨架（Week 1）

**目标**：架构跑通、模型选定、第一段 mp3 进入你的耳朵。

**做**：
- 3 个云函数（createTask / processTask / cronCleanup）
- 数据库 schema + 安全规则
- Provider 抽象层
- 6 个 skill 文件（第一版 prompt）
- Benchmark 脚本对比模型

**不做**：
- 除了一个"测试按钮"以外的任何 UI
- 用户身份 onboarding
- 订阅消息

**怎么测**：微信开发者工具的**云函数触发器面板**——直接传样本输入跑 processTask，听输出的 mp3。完全不需要 UI。

**退出条件**：你听了第一段 AI 生成的播客，拍板"这质量够听，继续做"或"哪个模型都不行，砍掉"。

### Phase 2：又丑又能跑（Week 2）

**目标**：真流程、真设备、锁屏能听到真播客。

**做**：
- 4 个最简陋的 UI（用 WeUI 或 TDesign 默认组件，零设计努力）
- 串起 `wx.cloud.callFunction` + `db.watch()` + BackgroundAudioManager
- 订阅消息
- Onboarding（一个屏幕，选身份）

**不做**：
- 视觉打磨、自定义配色、图标
- 动画
- 重生成功能（推 v2）

**退出条件**：你在手机上传一张小红书截图 → 关掉小程序去吃饭 → 收到推送 → 路上听完一篇。

### Phase 3：真实使用 7 天（Week 3）

**目标**：发现"实际什么烦人"，而不是"你以为什么烦人"。

**做**：**什么都不做**。就是用。

**做的事**：
- 每天用 1-2 次，连续 7 天
- 记一个 notes 文件："今天用的时候什么烦"
- **不要中途修**——让问题积累
- 周末按"频率 × 烦人程度"排序

**这是大多数项目跳过的阶段，也是最有价值的一步**。

### Phase 4：基于真实摩擦的打磨（Week 4+）

**目标**：处理实际摩擦，加你真正想要的东西。

**Phase 3 之后再决定要不要做的事**（不要预先承诺）：
- 重生成 + 文字反馈（原 v2 推迟项）
- 不懂的词手动勾选（如果 AI 自动判断漏得多）
- 播客时长选择器（5 / 10 / 20 min）
- 主题分类（如果时间线找不到了）
- 导出到外部 App

### 关于 PRD、Figma、设计工具

| 工具 | 建议 |
|---|---|
| **PRD** | 跳过。这份设计文档就是 PRD。加新功能就在文档里加新章节。 |
| **Figma** | 跳到 Phase 4+。4 个屏幕太简单，不值得预先设计。 |
| **WeUI / TDesign** | Phase 2 用作默认组件库——免费拿到 80% 的"看着不丑"。 |
| **设计参考** | Phase 2 前花 30 分钟截图 podcast app（小宇宙、Apple Podcasts、Spotify），指给 Claude Code："照这个抄"。比从零设计快。 |
| **v0.dev / Lovable** | Phase 4 可选——想 mock 某个屏幕时用，生成 HTML 让 Claude Code 翻译成 WXML。 |

### 核心原则：又丑又能跑 > 漂亮但坏

Phase 1-2 期间每个决策都问一句："**这是让它能跑，还是让它好看？**" 如果是"好看"，推到 Phase 4。Phase 3 真实使用会告诉你哪些"好看"项是真的重要。

### 反面教训：不要做的事

- ❌ **先在 Figma 画 4 个屏幕**——你 Phase 3 之后会想全推翻
- ❌ **先写一份完整 PRD**——你 Phase 1 之后会想改 50%
- ❌ **先打磨 UI 细节**（颜色、间距、动画）——Phase 3 会告诉你这些 90% 没人在乎
- ❌ **Phase 1 卡在"哪个模型最好"无法决断**——选个 top 2，Phase 2 跑通，Phase 3 真实使用后再回头切

## What I noticed about how you think

- 你能在我推出一份详细设计后，毫不犹豫地说"重新来过"——这是非常少见的能力。
- **你连续两次把我推回去读官方文档，而不是接受我的（带错误假设的）方案**——这是工程师的本能。AI 给的方案是默认起点，不是终点。
- 这种"先验证假设，再决定路径"的工作方式，正是用 AI 做产品最该养成的肌肉记忆。
- 新方向（消费产品）比旧方向（工作流工具）更聚焦，闭环更短，更容易验证"我会不会用"。
- "三者全要 + AI 自己判断怎么组合"——你信任 AI 做品味判断，而不是把所有决策都写死在 prompt 里。这是成熟的 AI 产品观。
